# The server half's flaky class: every `Deadline Propagation` permutation over TLS.
#
# Whether these pass is a property of the machine, not of the answer. Each case needs a TLS
# handshake inside a two-second deadline while the suite drives 48 RPCs at once, and a
# handshake here costs one RSA-2048 private-key operation in pure MoonBit — measured at 0.49 s
# (`@x509.signature_value` on a 2048-bit key). Forty-eight of those interleaved on one event
# loop cannot fit: each advances at a forty-eighth of the CPU and the first finishes around
# 24 s. The same cases pass with `-p 1`, and every other TLS case in the suite passes at full
# parallelism, so the server's TLS is correct and its RSA throughput is what falls short.
#
# Declared with `--known-flaky` rather than `--known-failing` for exactly that reason: the
# runner accepts either outcome here, so a faster machine that passes all seventy does not
# turn the build red, and a slower one that fails them does not either. They are still run and
# still reported — a case that fails is named in the output. `--known-failing` would have been
# wrong in both directions: it fails the run when a listed case passes.
#
# This list is not the whole statement. CI runs the class a second time with `--parallel 1` and
# nothing tolerated (`--run 'Deadline Propagation/**/TLS:true/**'`), because at one RPC at a time
# the handshakes no longer compete and all seventy pass. If that second run ever fails, this list
# stops being an explanation and becomes an excuse.
